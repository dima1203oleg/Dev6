# PREDATOR Analytics — Registry Correctness Test Specification

Мета документа: визначити, як перевіряти правильність, реальність, повноту та стабільність роботи всіх реєстрів і конекторів у production-середовищі PREDATOR Analytics.

Обсяг: усі 173 реєстри / джерела / конектори, включно з державними, комерційними та відкритими джерелами, які заявлені в Source Catalog.

Ключова вимога: система не має права показувати “ONLINE”, “HEALTHY”, “SUCCESS” або будь-який інший позитивний статус без реального успішного звернення до джерела та без збереження доказу запиту/відповіді.

⸻

## 1. ЩО ВВАЖАЄТЬСЯ КОРЕКТНИМ РЕЄСТРОМ

Реєстр вважається коректним лише тоді, коли одночасно виконані всі умови:

1. Джерело реально доступне за офіційним endpoint або документованим каналом.
2. Конектор виконує реальний запит, а не mock/stub/fake response.
3. Відповідь відповідає очікуваній схемі або коректно маркується як SCHEMA_CHANGED.
4. Отримані дані проходять парсинг без втрати критичних полів.
5. Нормалізація не створює вигаданих значень.
6. Усі факти мають provenance: джерело, час, request id, evidence id, hash.
7. Статус джерела відображає реальний стан, а не hardcoded status.
8. Відсутність даних не маскується під успіх.
9. Помилки авторизації, rate limit, timeout, schema mismatch і 5xx не маскуються під NO_DATA.
10. Результат можна повторити та перевірити повторним запитом або replay через evidence.

⸻

## 2. ЩО ПЕРЕВІРЯЄТЬСЯ

Тест повинен перевіряти такі рівні:

### 2.1. Рівень джерела
* чи існує джерело;
* чи доступний офіційний endpoint;
* чи є документація;
* чи потрібна авторизація;
* чи працюють ліміти;
* чи доступний реальний live response.

### 2.2. Рівень конектора
* чи реалізований конектор;
* чи не використовує fallback/mock;
* чи коректно будує запит;
* чи обробляє пагінацію;
* чи обробляє фільтри;
* чи обробляє помилки;
* чи записує evidence.

### 2.3. Рівень даних
* чи дані відповідають очікуваному типу;
* чи немає вигаданих значень;
* чи коректні дати, статуси, коди, ідентифікатори;
* чи немає дублювання;
* чи немає втрати критичних полів;
* чи відповідає структура схемі.

### 2.4. Рівень аналітики
* чи правильно працює entity resolution;
* чи правильно працює contradiction engine;
* чи коректно рахуються confidence scores;
* чи не підвищується впевненість без доказів;
* чи правильно формується граф зв’язків.

⸻

## 3. ЗАГАЛЬНІ ПРАВИЛА ТЕСТУВАННЯ
1. Для тесту використовуються реальні, законні, публічно доступні або дозволені тестові сутності.
2. Заборонено покладатися на персональні дані приватної особи як на єдиний тестовий сценарій.
3. Для кожного реєстру повинна бути мінімум одна позитивна перевірка і одна негативна перевірка.
4. Усі відповіді зберігаються як immutable evidence.
5. Жоден результат не вважається валідним без source provenance.
6. Якщо джерело недоступне, система повинна повернути правильний статус, а не підставляти інший.
7. Якщо schema змінена, система повинна це явно показати.
8. Якщо джерело повертає порожній результат, це NO_DATA, але тільки після реального запиту.

⸻

## 4. ТЕСТОВИЙ НАБІР
Для тестування слід створити три набори кейсів.

### 4.1. Позитивний набір
Сутності, які точно існують і мають підтвердження в офіційних або відкритих джерелах:
* юридичні особи;
* ФОП;
* реєстрові записи, що мають публічний статус;
* судові справи;
* санкційні згадки;
* відкриті закупівельні записи;
* ліцензії;
* декларації, якщо доступ дозволений.

### 4.2. Негативний набір
Запити, які мають:
* неіснуючий номер;
* неіснуючу назву;
* неправильний формат ідентифікатора;
* завідомо відсутній запис;
* недопустимий або порожній параметр;
* прострочений або недійсний доступ;
* перевищення rate limit;
* timeout simulation у тестовому середовищі.

### 4.3. Конфліктний набір
Запити, де різні джерела можуть мати:
* різні дати оновлення;
* різні адреси;
* різні ролі;
* різні статути;
* різні написання ПІБ;
* різні історичні значення.

⸻

## 5. ОБОВ’ЯЗКОВІ КРИТЕРІЇ КОРЕКТНОСТІ ДЛЯ КОЖНОГО РЕЄСТРУ
Кожен реєстр перевіряється за такими критеріями:

### 5.1. Доступність
* endpoint відповідає;
* TLS/HTTP працює;
* немає DNS/connection errors;
* є визначений timeout.

### 5.2. Авторизація
* API key / token / cookie / session працює;
* прострочені credentials дають коректну помилку;
* відсутні credentials дають AUTH_REQUIRED.

### 5.3. Схема відповіді
* response schema відповідає контракту;
* критичні поля присутні;
* типи значень коректні;
* масиви та пагінація працюють;
* версія схеми зафіксована.

### 5.4. Якість даних
* поля не порожні без причини;
* дати валідні;
* статуси з нормалізованого довідника;
* числові значення в межах допустимого;
* адреси, назви, коди не спотворені.

### 5.5. Доказовість
* збережений raw response;
* є hash payload;
* є timestamp;
* є connector version;
* є parser version;
* є request id;
* є source id.

### 5.6. Повторюваність
* той самий запит дає прогнозований результат;
* зміни між запусками пояснюються реальними оновленнями джерела;
* немає випадкових або синтетичних значень.

⸻

## 6. СТАНДАРТНИЙ ПРОЦЕС ТЕСТУВАННЯ ОДНОГО РЕЄСТРУ
Для кожного джерела виконується така послідовність:
1. Перевірити metadata джерела.
2. Перевірити, що джерело зареєстроване в Source Catalog.
3. Перевірити, що конектор не є mock/fallback.
4. Виконати health check конектора.
5. Виконати реальний live request.
6. Перевірити HTTP status та заголовки.
7. Перевірити структуру відповіді.
8. Перевірити парсинг.
9. Перевірити нормалізацію.
10. Перевірити запис evidence.
11. Виконати повторний запит для перевірки стабільності.
12. Зіставити результат із еталонним очікуванням.
13. Занести результат у certification matrix.

⸻

## 7. ТЕСТИ, ЯКІ МАЮТЬ БУТИ НА КОЖНОМУ РЕЄСТРІ

* **Тест 1. Реальний доступ:** підтвердити, що джерело відповідає реально (валідний HTTP response, без mock).
* **Тест 2. Авторизація:** перевірити, що джерело правильно обробляє наявність або відсутність доступу.
* **Тест 3. Валідний запит:** перевірити типовий правильний запит.
* **Тест 4. Невалідний запит:** перевірити помилки формату (INVALID_QUERY, VALIDATION_ERROR).
* **Тест 5. Порожній результат:** перевірити, що джерело може чесно повернути відсутність даних (NO_DATA).
* **Тест 6. Rate limit:** перевірити обробку обмежень (RATE_LIMITED).
* **Тест 7. Timeout:** перевірити стійкість до затримок (TIMEOUT, SOURCE_UNAVAILABLE).
* **Тест 8. Schema drift:** перевірити зміну структури відповіді (SCHEMA_CHANGED).
* **Тест 9. Дубль:** перевірити дедуплікацію (один evidence, одна normalized entity).
* **Тест 10. Replay:** перевірити відтворюваність із raw evidence.

⸻

## 8. ЩО ВВАЖАТИ ПОМИЛКОЮ
Реєстр вважається некоректним, якщо:
* повертає mock або synthetic data в production;
* показує ONLINE без реального запиту;
* повертає SUCCESS, хоча API насправді недоступне;
* маскує помилки авторизації як NO_DATA;
* створює вигадані поля;
* втручається у факти під час нормалізації;
* не зберігає provenance;
* не відрізняє старі й нові дані;
* не відображає schema mismatch;
* не проходить replay із raw evidence.

## 11. ACCEPTANCE CRITERIA
Система проходить тест на коректність реєстрів лише якщо:
1. Усі 173 реєстри мають визначений status.
2. Для кожного джерела відомо, чи воно реально працює.
3. Немає mock fallback у production path.
4. Усі дані мають provenance.
5. Усі критичні запити можуть бути replayed.
6. Помилки класифікуються правильно.
7. Schema drift не ламає систему мовчки.
8. Entity resolution не змішує різні сутності.
9. Confidence score обґрунтований доказами.
10. У звіті видно різницю між: success, no data, unavailable, auth required, rate limited, schema changed.

3. Потім запустити negative tests.
4. Потім schema drift tests.
5. Потім replay tests.
6. Потім end-to-end tests із entity resolution.
7. Потім production certification.

⸻

## 14. ФІНАЛЬНА ВИМОГА
Реєстр не вважається коректним просто тому, що він існує в каталозі. Він вважається коректним лише тоді, коли:
* реально відповідає;
* повертає правильну структуру;
* не бреше про статус;
* не підміняє дані;
* не працює через fallback;
* має evidence;
* може бути перевірений повторно;
* дає передбачуваний і пояснюваний результат.

⸻

## 15. ВИСНОВОК
Для PREDATOR Analytics тест на коректність реєстрів повинен бути не “чи щось повернулося”, а:
чи повернулося саме те, що реально існує в джерелі, чи це можна довести, і чи система чесно показує статус кожного джерела без фальші.
